# 已退役记忆的追溯意图门控召回设计

> 日期：2026-10-16
> 状态：待项目所有者复核
> 范围：场景二（夜话会话）情景记忆检索门控；场景一（日记分析）不在本次范围
> 关联：`server/app/domain/memory/conflict.py`（软覆盖）、`server/app/domain/memory/episodic.py`（情景存储与检索）、`server/app/infrastructure/memory_repository.py`（持久化过滤）

## 1. 背景与问题

### 1.1 现状机制（代码实况）

情感反转软覆盖的处置链路：

- **触发**：`conflict.py` `detect_person_conflicts` —— 人物已在 `important_people`、新情感与画像旧情感异号、且 `|Δ| ≥ 0.6`
- **退役**：`supersede_outdated_entries` —— 对与旧画像**同号**的条目打上 `superseded_by` 指针（排除触发条目本身与已退役条目）
- **可见性**：`memory_repository.load_entries` 默认只返回 `superseded_by is None` 的条目；原文保留在库中供审计（`include_superseded=True` 路径）

### 1.2 问题

三处错配：

- **P1 两个问题共用一把闸门**：Q1「该不该影响当下状态判断」（如安慰刚吵完架的用户时不该说"你们关系真好"）与 Q2「还该不该被召回」（如用户问"我和 TA 这些年是怎么过来的"）被同一个过滤回答。当前实现用「退出检索」回答了 Q1，代价是否定了 Q2。
- **P2 退役粒度是整条 entry**：失效的只是「对某个人的旧观点」这一侧面，但被退役的是整条记忆（「今天 TA 帮我改简历，顺便被老板骂了一顿」整条消失）。
- **P3 证据单向化**：退役后该人物的可召回证据只剩负面，可能反向放大负面框架。

本 spec 只解决 **P1 在检索侧的表现**（追溯语境下不可召回）。P2 为独立轴（轴 B），另行立项；P3 不在本次范围。

### 1.3 决定实现形态的事实约束

过滤发生在**装载期**而非查询期：`episodic.py` 的 `load()` 调用 `load_entries(user_id)` 使用默认参数（排除已退役），进程内 deque **从来不含**已退役条目。因此"查询时按意图放行"不是加一个过滤参数即可——池子里根本没有这些条目，必须显式从存储读取。

### 1.4 已核实的前置依赖

检索调用点 `conversation_ai_service.py` 的两处 `_format_episodic_memories(container, retrieval_query)` 调用，其上一行作用域内已在用 `intent_result.intent_category`（debug 日志）。**意图在检索点已可用，无需新增分类调用。**

## 2. 目标与非目标

### 目标

1. 追溯意图下，已退役条目可被召回
2. 召回的历史条目**必须带时效标注**，不得冒充当前状态
3. 非追溯语境与危机语境下，行为与本改动前逐字节一致
4. 门控为确定性逻辑，可被单测覆盖，**不引入新的 LLM 调用**

### 非目标

- 不改退役条件与退役粒度（轴 B 独立立项）
- 不纳入场景一（日记分析路径）——其检索侧表现另行评估
- 不改 `retrieve_relevant` 对外行为（deque 容量、decay 过滤、排序权重均不变）
- 不做降权式软召回（见 §5）
- 不改危机安全分层

## 3. 设计

### 3.1 门控语义

- **放行**：`retrospective_query`、`retrospective_review`
- **排除**：其余全部（含 `emotional_support` / `advice_seeking` / `casual_chat` / `pure_record` / `habit_tracking`）
- **红线**：危机语境**永不**放行，且不可被 intent 参数绕过。以独立断言固化在代码与测试中，不依赖调用方自觉

### 3.2 实现形态

- 抽出 `_rank(candidates, query, top_k)`：排序逻辑**单一实现**，两个入口共用
- `retrieve_relevant(query, top_k)`：对外行为不变，内部委托 `_rank`
- 新增 `retrieve_including_superseded(query, top_k)`：定向存储读取 `include_superseded=True` → `_rank`
- 调用点：`_format_episodic_memories(container, query, *, allow_superseded: bool = False)`
- **默认 `False`**：未显式放行的调用点零行为变化（场景一安全）

拒绝「把已退役条目装进 deque、在查询期过滤」的变体：会占用 `MAX_ENTRIES` 容量并参与 decay 过滤，可能挤掉活跃条目。

### 3.3 注入形态（放行 ≠ 复原）

召回后**必须带时效标注**，否则等于重新打开已修好的漏洞：

1. 独立成节：`【历史记忆（已被后续经历修正）】`，与「相关日记记忆 / 夜话共鸣 / 情绪卡片」并列
2. 逐行标注：`- [情绪] 事件摘要……（该感受此后已变化，最新倾向：…）`
3. 排序与配额：当前态记忆在前；历史最多占 `top_k` 中的 2 席，防止历史挤掉当下事实

### 3.4 降级与边界

- 存储读取失败 → 退回现状检索（排除），记 debug，**不阻断回复**
- 同一 entry 在两节同时出现 → 只保留当前态节
- 检索结果为空 → 历史节不渲染（模板保持字节稳定）

## 4. 改动点（仅场景二）

| 文件 | 改动 |
|---|---|
| `app/domain/memory/episodic.py` | 抽 `_rank`；新增 `retrieve_including_superseded` |
| `app/services/conversation_ai_service.py` | `_format_episodic_memories` 增 `allow_superseded` 参数与历史节渲染；两处调用点传参 |
| `app/domain/memory/conflict.py` | 不改（退役语义不变） |
| 意图常量 | 实施时确认 `retrospective_query` / `retrospective_review` 的常量名与取值来源 |

危机标记若不在该调用点作用域内，需向上传递；**禁止以「intent 是追溯」为由放行**。

## 5. 被否决的方案

- **降权而非剔除**：把安全属性从「确定性排除」退化为「大概率不出现」——与危机安全的确定性原则冲突；且它改的是排序动力学，评测面最大
- **deque 内放行 + 查询期过滤**：容量与 decay 副作用（见 §3.2）
- **时效摘要注入**：硬门槛不变，仅在 prompt 注入一行摘要；模型看不到原文，信息损失未解决
- **纳入场景一**：本轮范围外

## 6. 测试策略

**确定性单测**（无需统计校准）：

- 门控表：参数化覆盖全部意图的放行/排除
- 危机红线：crisis 下即使 intent 为追溯，断言零退役条目进入上下文
- 排序单源：断言两个入口共用 `_rank`（防止排序行为漂移）
- 格式化：历史节存在、标注文案正确、配额 ≤ 2、空结果不渲染
- 回归：非追溯意图下 `_format_episodic_memories` 输出与改动前**逐字节一致**

**评测门**：三臂 A/B（现状硬剔除 / 本机制 / 无过滤基线）+ 新增追溯型用例组。北极星指标：追溯轮中旧记忆被召回**且**被标注。**+1.58 的既有结论不假设继续成立，需重跑。**

## 7. 风险

- **R1 历史条目被模型当作当前状态** → 由 §3.3 时效标注 + 配额约束缓解；评测用例覆盖
- **R2 追溯轮新增一次存储读取** → 追溯意图低频，且读取为单用户有界集合
- **R3 排序逻辑抽取引入行为漂移** → 单源 `_rank` + 逐字节回归断言兜底

## 8. 验收标准

1. 单测全绿（新增用例 + 既有回归）
2. 非追溯语境的上下文输出逐字节不变
3. 危机红线断言通过
4. 评测门三臂对照完成、结论落库；指标下降则回退
5. 场景一未受影响（其调用点未传参）
