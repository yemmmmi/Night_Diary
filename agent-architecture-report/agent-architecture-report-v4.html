SECTION 01

金字塔总览：一个论点，五根支柱

本节结论 面试官问"你的项目里 Agent 体现在哪"，答案不是"接了个大模型 API"，而是五根支柱： ①编排（四入口分治 + 同步/流式语义分离）②记忆（三层记忆 + 四维守门） ③检索（混合 RAG + 心理学知识库）④数据（业务数据 → 记忆原子 → 行为闭环） ⑤评估（9 套目录，按 REAL / stub / oracle 与 CI 状态披露）。每层都能展开到具体类名、参数与限制。

1.1 为什么这五根支柱恰好是秋招考点

面向 2027 届秋招，公开官方 JD 的方向性要求集中在： Agent 编排框架（LangChain/LangGraph）、RAG 全链路、记忆与上下文管理、工程化上线能力。 更内核化的岗位（腾讯智能体平台、Harness Engineering）则直接考察"Agent Loop、多 Agent 协作、Memory、Skill、任务规划、工具调用、状态管理、异常恢复"[5]。 五根支柱与这两组考察面一一对应，且 v3 补齐了 v2 报告承认的两个最大缺口：LangGraph 框架经验与原生工具调用。

2.4 原生工具调用循环：bind_tools 优先，文本协议兜底

v2 报告承认的最大缺口"无原生 Function Calling"在 v3 已解决。services/ai/tool_factory.py 定义 8 个本地工具： search_diary（日记检索）、analyze_sentiment（情绪分析）、query_entity_graph（实体图谱查询）、 list_todos（待办列表）、get_plan_progress（计划进度）、get_plan_detail（计划详情）、 get_weather_info（天气）、get_user_address（地址）——全部为标准 ToolSpec 结构。 工具的统一入口是 ToolRegistry（见 2.5），执行协议分两级：

  • 原生层：supports_native_tools(llm) 通过且有工具规范时，llm.bind_tools(tool_specs) 绑定后由模型自主决策调用，extract_native_tool_calls() 解析响应——真正的 Function Calling 循环；
  • 兜底层：bind_tools 抛异常（模型不支持 / 协议不兼容）时降级为文本标签协议，把工具规范注入 prompt 让模型以文本形式表达调用意图；
  • 循环控制：最多三轮属于 run_conversation_loop_streaming 与 legacy fallback；LangGraph 六节点图是 single-pass，不能把两者混写；
  • 意图过滤：进入循环前按 intent_result.need_tools 过滤本地工具——闲聊意图拿不到任何工具，从源头降低误调用；MCP 工具例外：绕过白名单常驻可用集，由 LLM 自主决策是否调用（设计动机见 2.5）。

2.5 ToolRegistry 与 MCP 工具生态：本地 8 工具 + 远程 N 工具一条总线

上一版报告把"MCP 未接入"列为 P0 缺口——本版已修复。services/ai/tool_registry.py 的 ToolRegistry 是"Agent 能用什么工具"的唯一事实源：本地工具按请求重建（绑定 user_id），MCP 连接进程级共享（共享进程模型， 每端点一条连接，user_id 逐调用记录）。核心设计：

关注点实现（实测）
配置解析MCP_ENDPOINTS（alias:url，SSE/HTTP）与 MCP_STDIOS（alias:command args key=value，子进程）——坏行逐条隔离，一条配置错误不阻塞其余端点
三种传输URL 以 /mcp 结尾自动选 Streamable HTTP（会话独立，重连安全），/sse 走 SSE；stdio 由 mcp SDK spawn 并托管子进程，env 键值注入且永不进参数快照
异步桥接mcp SDK 是 asyncio-only 而工具函数是同步的——McpLoop 用一条常驻后台事件循环线程统一 marshal 所有协程，规避"session 建在 loop A、用在 loop B"的 asyncio.run 陷阱

健康与自愈调用失败 → 指数退避重启（1s/2s/4s）后重试；重试耗尽进入 dead 后从 Agent 工具集摘除，后续懒恢复成功再重新发现，并有 dead → 摘除 → 恢复测试

MCP 工具绕过意图白名单是这里最值得讲的取舍：本地工具按意图过滤（闲聊不给工具），MCP 工具则常驻可用集， "该不该调"完全交给 LLM 决策。理由：外部工具的能力面在配置时不可枚举（意图表无法预知一个新接入的搜索/抓取工具该绑定哪个意图）， 与其维护一张猜不准的映射表，不如让决策层（bind_tools 循环）自己判断——代价是 D1 的决策短板现在也作用于 MCP 调用（见缺陷 D3）。

生产落地经过一次真实的踩坑迭代：最初用 supergateway 把 stdio server 桥接成 SSE 容器，但该桥只允许一个客户端、重连即崩 （"Already connected to a transport"），且 npm 依赖在构建环境不稳定。最终方案是官方 Python 版 mcp-server-fetch 直接打进后端镜像， 由 MCP_STDIOS=fetch:python -m mcp_server_fetch 以 stdio 子进程托管——免 API key、免网关、随 backend 一起起； 确实需要独立进程或 API key 的工具（如 tavily）才走 --profile mcp 容器，且改用 --outputTransport streamableHttp（/mcp 路径， 多客户端安全）。连接层相应升级为 http_connection() 工厂：URL 以 /mcp 结尾自动选 Streamable HTTP，否则走 SSE——传输选择从配置项变成约定，配置面只剩一个 URL。

异步桥接是面试加分点："mcp SDK 只支持 asyncio，而我的 agent 工具是同步签名——我没用 asyncio.run 每次现起事件循环， 因为那会踩'session 建在 loop A、用在 loop B'的坑；我起了一条常驻后台线程跑唯一的事件循环，所有 MCP 协程统一 marshal 过去， 调用侧保持同步阻塞语义、带 30s 超时。这是把异步边界收敛到一处的架构决策，不是随手写个 run()。"

4.1 查询理解：指代消解 + 陈述式改写

query_understander.py 在检索前先"听懂"问题：规则层用指示词模式做指代消解（"那件事" → "之前的经历"等映射表）， 用疑问句模式做陈述式改写（"为什么 X" → "X 原因"、"X 怎么办" → "X 困扰"），并抽取关键词； LLM 层在规则置信不足时介入（规则层置信 0.7，LLM 结果需 ≥ 0.85 才采纳，低于阈值时与规则结果合并取优）。 改写后的 query 才进入检索——对抗"用户问'那后来呢'"这类零信息查询的第一道工程手段。

4.2 混合检索：双路召回 + RRF 融合 + 交叉编码器重排

HybridRetriever（domain/rag/retriever.py）默认参数：语义路 top 20（Chroma 向量） + 关键词路 top 20（BM25，jieba 分词，k1=1.5 / b=0.75）→ RRF 融合（k=60） → reranker 重排 top 5：工作区默认云优先 Qwen text-embedding-v3 + qwen3-rerank，本地 BAAI/bge-reranker-base 为降级。 两个防脏细节：孤儿向量过滤（以 BM25 索引的已知文档集为准， 剔除向量库中已被删除日记的残留向量）与按 diary_id 去重（同一日记多 chunk 只留最优）。

分块策略（chunker.py）：标准模式 chunk 512 / 重叠 50 / 最小块 128， 支持中文分隔符降级切分；可选 parent-child 模式（child 250 / 重叠 30）。v3 新增 card_chunks 集合——卡片整条 upsert 不分块， 检索面从日记扩展到卡片。

5.2 四条数据链路：从用户动作到 Agent 再回来

链路 A · 手写日记（保存与生成解耦）

链路 B · 卡片（最轻的链路）

POST /cards → card_service.create_card 落库 → refresh_cards_section 刷新当日摘要卡片段（纯聚合，零 LLM 调用，且不再触发整段重建）→ sync_card_to_episodic 直接转情景记忆 → v3 新增：卡片整条 upsert 进 card_chunks 向量集合（不分块），检索面从日记扩展到卡片。 卡片还能 expand_to_diary 展开后显式调用 trigger_analysis，由 treehole 生成 1–3 句短回信并写 AnalysisRow/reply——这是短回信入口，不应与手写保存混同。卡片与摘要共享北京时间（UTC+8）日界。

链路 C · 计划（唯一的行为闭环链路，v3 三模板落地）

计划技能从对话生成 PlanRow（source=agent + created_from_conversation_id 回链 + template 三选一）→ 里程碑模板的任务可带联网搜索所得 multi_source 多来源候选 → 用户执行：打卡模板累计签到 / 计时模板 start_timer→stop_timer 写 PlanCheckinRow / 里程碑任务逐个 done → 任务状态变更时 ContentNormalizer.from_task 生成记忆原子（importance 固定 0.6，tags 含计划名）→ 经 MemoryGateway 入情景记忆 → 周报聚合统计计划执行率。 至此"计划 → 执行 → 记忆 → 洞察 → 新计划"闭环成立。

链路 D · 周报（聚合视图链路）

weekly_service 聚合本周日记 + 卡片 + 活跃计划及任务快照 → ExecutionPlanner.execute() → MultiAgentGraph（Supervisor + Workers）→ WeeklyReportRow 存正文与统计 → 前端复盘展示。

实体抽取的"零 Token"设计：第一层纯正则（人物：亲属称谓 / 老小阿+名；地点：城市与场所词；话题：行为与情绪词）召回， 只有正则命中候选时才进入第二层 LLM 精炼（分类、关系标注、情感倾向），把实体抽取的 LLM 成本压到"按需付费"。 图谱侧 Neo4j MERGE 出 (User)-[MENTIONS]->(Entity) 与 RELATED_TO 关系；Neo4j 不可用时降级 SQLite。

MCP 工具常驻可用集、绕过意图白名单；第 9 套评测的 baseline.json 仍是 stub oracle placeholder（model/parser 1.0）。2026-09-09 三次 REAL 质量门均打印 model_exact=0.7500 / parser_exact=1.0000（12 例，deepseek-v4-flash），但没有写入 baseline，因此不能当质量门禁引用。
根因
MCP 批次优先打通传输与观测；decision 评测 harness 已能 REAL 跑，缺的是把结果写成带 _mode/_model/_sample_count 的合同并设阈值。
影响
面试被问"MCP 工具误调用怎么办"时，目前有一次 0.75 的试跑观察，没有入库合同与回归阈值；线上一次误调用仍带来真实外部请求成本。
优化方向
把三次试跑之一写入 REAL baseline，再讨论 decision ≥ 0.85 一类阈值；与 D1 的 native 0.75 分开讲：一个是本地工具、一个是 MCP 决策，都还没过合同门槛。
D4同步图异常曾被内部 fallback 吞掉，图级回退名不副实已关闭 · 当前快照
原现象
run_conversation_graph() 捕获 graph.invoke 异常并直接返回固定文案，调用方无法进入 legacy loop。
根因
图适配层和调用层同时承担降级，异常边界重叠。
修复
图适配层不再吞执行异常，由 run_conversation_loop() 统一捕获并调用 legacy loop；故障注入测试断言最终回复确实来自 legacy LLM。
剩余边界
节点内部有意转成业务 fallback 的可恢复错误仍不会触发整图重跑；报告只承诺“未被节点消费的图执行异常”回退。
D5多轮评测样本量小；词面命中与 Judge 忠实度不必混为一谈P2 · 小样本残余风险
现象
2026-09-09 REAL：多轮 coherence 1.00（3/3）、忠实度 5.00、overall 4.93；洞察忠实度 4.60 / overall 4.64。旧报告的 coherence 0.67 / 忠实度 2.67 来自 Judge 未注入 history 与词面闸门，已失效。mt02 的 literal topic hit 仍为 no，但不参与质量门。
根因
评测口径修好后，短板从"上下文丢失"变成"n=3 方差大"。多轮状态仍走压缩上下文（1500 Token 压缩 + 4000 Token 工作记忆），信息有损的工程风险还在，只是当前 3 个场景没有把它打出来。
影响
不宜再把 2.67 当主动讲的短板；面试应主动说明样本量与词面诊断项，避免被追问时拿出过期数字。
优化方向
扩多轮评测集到 10+ 场景降低方差；保留 lexical hit 作诊断、质量门继续用 faithfulness。不必为了粉饰 n=3 满分去改 prompt。
D6危机检测是纯关键词 + 词表加权规则，无召回兜底模型P1 · 伦理追问必备
现象
CrisisGuard 依赖重度负面词表 + 情绪评分阈值（−0.7）；委婉表达、隐喻或中英混杂可能漏检。
根因
规则优先是为延迟与确定性：危机拦截在路由层，必须毫秒级、零依赖。
影响
漏检的伦理与合规风险；面试官问"误报率怎么权衡"需要完整答案。
优化方向
两级方案：关键词层保留（保延迟），异步轻量分类器复核（保召回）；评测集补危机委婉表达用例并设 safety 地板断言（生成质量套件已有此机制可复用）。
D7异步任务无幂等键、无重试策略，线程降级会丢任务P1 · 分布式考点
现象
JobRow 有 status/attempts 字段但无去重键；RQ 单队列无自定义重试；Redis 不可用降级 daemon 线程，进程重启任务即丢；_run_safe 仅记日志不重投。
根因
队列从"单机可用"起步，幂等键需要业务侧约定（如 user_id + diary_id + kind）。
影响
记忆写入或实体抽取静默丢失时，用户无感知但数据不完整——分布式面试的经典考点。
优化方向
任务入队带幂等键（唯一索引去重）；失败任务进死信表可人工重放；启动时扫描 pending 超时任务重投。
D8心理学知识库向量集合无自动种子机制P1 · v3 新增组件的欠账
现象
PSYCHOLOGY_ENTRIES（22 条理论）只被洞悉技能的静态轨按关键词消费；Chroma 向量集合 domain_knowledge_psychology 的写入接口存在，但没有启动时 / 部署时自动播种——集合在全新环境是空的，Agent 向量轨实际检索不到知识。
根因
知识库是 v3 末段新增模块，种子脚本还没进 Makefile / docker entrypoint。
影响
"三个 Agent 注入领域知识"的设计在生产新环境会静默失效（prompt 自动省略知识段，无报错）；演示时如果环境是新的，向量轨讲不出来。
优化方向
半天：启动时检测集合并按需 upsert 22 条理论（幂等，按条目 ID）；加一条集成测试断言集合非空。
D9长期画像晋升规则单一：只认"连续 3 天 tag 复现"P2 · 坦然承认的权衡
现象
晋升只看 tags / emotions 是否连续 3 天出现；无语义聚类，无跨周主题漂移检测；tags 质量依赖上游抽取。
根因
刻意用规则替代聚类：可解释（"为什么晋升"一句话答清）、零成本、无超参调优负担。
影响
换说法表达同一话题（"加班"/"项目忙"）不会被识别为重复话题；画像更新偏保守。
优化方向
topic 级 embedding 聚类 + 规则双通道；画像字段版本化。适合作为"如果重做会怎么改"的答案。
D10技能层与工具层两套联网能力并存：plan_skill 自带搜索未走 ToolRegistry 总线P2 · 边界权衡
现象
计划技能的联网参考链接由技能内部直连 Tavily → DuckDuckGo 两级搜索获得；笔谈 Agentic Loop 的工具则走 ToolRegistry（本地 8 + MCP）。同一"联网查证"能力存在两份实现，观测口径也不同——技能侧搜索不产生 mcp_call_logs / S8_mcp span。
根因
技能是 LangGraph 之外的确定性短路路径，引入工具循环会拉长延迟；多来源候选排序与技能产出强耦合。
影响
未来若把联网搜索整体迁到 MCP 工具，需要两处改造；面试被问"为什么技能不走工具循环"需备好延迟与确定性的理由。
优化方向
把 web_search 封装成 ToolRegistry 工具供技能层复用（保留短路结构，只统一传输与观测口径）；或保持现状并记录边界。适合作为"如果重做会怎么改"的备选答案。

10.3 面试高频追问与应答要点

为什么 v3 从自研编排换成 LangGraph？
结论先行：同步笔谈需要显式状态、节点边界和条件路由，LangGraph 让六阶段执行图可检查、可测试。当前图的工具节点是 single-pass，并不冒充多轮 ReAct；需要最多三轮工具回填的路径仍由独立 streaming / legacy loop 承担。自研循环没有删除——未被节点消费的 LangGraph 执行异常由调用层捕获并回退 legacy，故障注入测试验证了回复来源。
原生工具调用准确率只有 0.75，为什么还敢写在简历上？
先给结论再拆数字：0.75 是"决策准确率"，工具名 0.90、参数 0.88——错在"该不该调"而不是"怎么调"。根因是 LLM 倾向宁可多调（误调用率 0.60，主要失败在情绪表达场景）；fallback 文本协议全对但工具覆盖窄。我的行动：决策 prompt 加拒绝调用的 few-shot、工具描述补"何时不调用"、评测集持续收集负例。把短板做成量化故事，比藏起来强。
记忆为什么会"忘"？丢数据吗？
三层答案：情景记忆 100 条 LRU 上限 + importance ≥ 0.5 写入阈值 + 7 天半衰期衰减——设计上就是"主动遗忘"，因为检索质量比记忆数量重要；SQL 持久层全量保留（payload_json），LRU 只淘汰内存索引；被晋升进长期画像的洞察永不衰减。
RAG 为什么必须混合检索？单向量不行吗？
用数字答并附边界：2026-09-09 Qwen REAL 质量门上，BM25 recall@5 为 0.667，向量为 0.967（MRR 1.00），RRF 为 0.950，qwen3-rerank 后 recall 仍 0.967、MRR 0.95。情景记忆上向量单路 0.348 反而弱于 Jaccard 0.498，重排后到 0.564——所以混合不是教条，是数据。小样本只作回归基线，不证明任一环节在所有线上查询中都不可替代。
多跳检索会不会越查越偏？
会，所以做了两道守护：改写查询与原查询相似度低于 0.3 锚点阈值即判"查询漂移"停止；命中不足且已有 ≥2 条高相关结果时提前收敛。上限 3 跳，成本可控。
怎么评估一个 Agent 的好坏？
分层评估：组件层用检索指标（recall/MRR/nDCG）与分类指标（accuracy/F1）；行为层用工具调用与技能激活的准确率/误激活率；生成层用 LLM-as-Judge 的 rubric 加权评分（安全 ×1.5 且有地板断言）；成本层盯 Token 与延迟。全部对 baseline 做回归，而且 v3 把 stub 模式评测挂进了 CI——指标回退超过容差直接挡提交。
接 MCP 时踩过什么坑？为什么不用现成的网关方案？
踩过两个真实的坑。其一，supergateway 桥接：最初把 stdio server 桥成 SSE 容器，但它只允许一个客户端、重连即崩（"Already connected to a transport"），npm 依赖在构建环境还不稳定——最终换成官方 Python 版 mcp-server-fetch 直接打进后端镜像，stdio 子进程托管，免网关免 API key。其二，异步边界：mcp SDK 是 asyncio-only 而工具函数是同步签名，我起了一条常驻后台事件循环线程统一 marshal 所有协程，避免"session 建在 loop A、用在 loop B"的坑。两个坑的共性是：集成方案的选型标准是"故障域最小"，不是"配置最少"。
LangGraph 挂了 / LLM 挂了 / Redis 挂了 / 用户发危机内容，分别会怎样？
编排层：未被节点消费的 LangGraph 执行异常回退 legacy loop，bind_tools 不兼容回退文本协议。模型层：tier → default → 环境变量仍不可用时，由各调用路径返回确定性 fallback 或报告 AI 不可用；stub 只用于测试/缺依赖环境。组件层：Redis 回退内存 dict，队列退化 daemon 线程。危机路径：输入检测改走安全回复、记忆层拒绝写入防污染、路由收缩、流式缓冲与滑窗拦截，命中即撤回替换。
